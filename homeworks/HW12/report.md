# HW12 – временные ряды: temporal split, baseline-модели и GRU-прогноз

## 1. Кратко: что сделано

- Использован датасет S12-hw-dataset.csv, задача — прогноз следующего значения временного ряда target.
- Данные отсортированы по времени, выполнен корректный train / validation / test split без перемешивания.
- Сравнены подходы: B1 (naive-last), B2 (moving-average), B3 (ridge-lag-features), R1 (GRU).
- Лучшая модель выбрана по validation MAE: ей оказалась GRU (R1).

## 2. Среда и воспроизводимость

- Python: 3.13
- pandas / numpy / scikit-learn: стандартные версии из Anaconda
- torch: PyTorch (CPU)
- Устройство (CPU/GPU): CPU
- Seed: 42
- Как запустить: открыть `HW12.ipynb` и выполнить Run All.

## 3. Данные и постановка задачи

- Датасет: `S12-hw-dataset.csv`
- Целевая колонка: target
- Частота временного ряда: почасовая
- Горизонт прогноза: 1 шаг вперёд
- Размер датасета: 4320 наблюдений
- Диапазон дат: 2025-01-01 — 2025-06-29
- Есть ли дополнительные внешние признаки: нет (используются только производные от target)
- Комментарий (2-4 предложения): В ряде наблюдается выраженная сезонность (вероятно суточная), а также колебания без сильного долгосрочного тренда. Значения достаточно шумные, но без явных выбросов. Пропусков в данных не обнаружено. Задача прогнозирования умеренной сложности из-за сезонности и локальной вариативности.

## 4. Temporal split и признаки

### 4.1. Разбиение по времени

- Как именно выполнен `train / validation / test`: train: 70%
validation: 15%
test: 15%
- Какие доли или интервалы использовались: train: 2025-01-01 → 2025-05-06
validation: 2025-05-07 → 2025-06-02
test: 2025-06-03 → 2025-06-29
- Почему `random split` здесь некорректен: Временные ряды требуют прогнозирования будущего по прошлому. При случайном перемешивании возникает утечка информации, так как модель может видеть будущие значения при обучении.

### 4.2. Признаки для baseline-моделей

- Какие лаги использовались: lag_1, lag_7, lag_14
- Какие rolling-признаки использовались: rolling_mean_7, rolling_std_7
- Какие календарные признаки использовались: hour, dayofweek, day, month, is_weekend
- Как обрабатывались пропуски после построения лагов/rolling: строки с NaN после лагов и rolling удалены (dropna)
- Использовалось ли масштабирование и где именно оно обучалось: для B3 использован StandardScaler, обученный только на train

## 5. Модели и эксперименты (B1, B2, B3, R1)

Опишите коротко и сопоставимо:

- B1 (`naive-last`): прогноз = последнее известное значение
- B2 (`moving-average`): прогноз = скользящее среднее (окно 24)
- B3 (`ridge-lag-features`): Ridge-регрессия на лаговых, rolling и календарных признаках
- R1 (`gru-forecast`): GRU на оконном представлении ряда

Дополнительно:

- Основная метрика выбора лучшей модели: MAE (validation)
- Дополнительные метрики: RMSE, MAPE, sMAPE
- `window_size` для `GRU`: 24
- Batch size: 64
- Максимальное число эпох: 20
- Optimizer: Adam
- Learning rate: 0.001
- Как сохранялась лучшая модель: validation MAE (state_dict)

## 7. Анализ

Наивный baseline (B1) показал относительно неплохие результаты, что говорит о сильной автокорреляции ряда. Это типично для временных рядов с выраженной локальной зависимостью.
Moving average (B2) оказался значительно хуже, так как сглаживание теряет локальные колебания и плохо подходит для предсказания следующего значения в шумном ряде.
Добавление лаговых, rolling и календарных признаков (B3) улучшило качество модели, так как позволило учитывать сезонность и краткосрочные зависимости. Ridge-регрессия эффективно использует эти признаки, но остаётся линейной моделью.
GRU (R1) показала наилучший результат, так как способна моделировать последовательные зависимости во времени и учитывать сложные паттерны в данных.
В ряде явно присутствует сезонность (вероятно суточная), что объясняет эффективность лагов и оконного подхода. Тренд выражен слабо, но вариативность высокая.
Потенциальные утечки могли возникнуть при неправильном построении лагов или использовании future-информации, однако в данной реализации они исключены (используется shift и temporal split).
Выбор модели по validation принципиален, так как использование test для выбора приводит к переоценке качества и некорректной оценке обобщающей способности.
Ошибки модели наиболее заметны в пиковых значениях ряда, где наблюдается высокая вариативность.

## 8. Итоговый вывод

Для данной задачи в качестве базового подхода можно использовать модель на лаговых признаках (Ridge), так как она даёт стабильный результат и проста в реализации.
Однако GRU показала лучшее качество, поэтому при наличии ресурсов имеет смысл использовать нейросетевые методы.
Простые baseline могут быть достаточны при ограниченных требованиях к качеству, но для более точного прогноза лучше применять модели, учитывающие временную структуру данных.
Главный вывод — корректный temporal split и отсутствие утечек важнее выбора конкретной модели.
